A Bazel action runs once per *action key*, and the action key is a hash of
everything Bazel can prove the action depends on. When two builds compute the
same key, the second one short-circuits and reuses the first one's outputs.
That is the whole pitch.

The interesting question is not how the cache works. It is what counts as an
input.

## What's in the key

For every action, Bazel hashes:

- The **command line** that will be run.
- Every **input file's content hash**.
- A list of **output paths** the action will declare.
- The **execution platform** (linux-x86_64 vs darwin-arm64 vs whatever).
- The **environment variables** the action declares it reads, and their
  current values.

That last bullet is the one people get wrong.

## The environment-variable trap

By default, an action sees an almost empty environment. The variables it
*does* see — the ones declared via `--action_env` or set in `env` on the rule
— are part of the cache key. Change `LANG` between builds, and any action
that lists `LANG` in its env gets a fresh key and a fresh execution.

This is good. It is also the source of the bug I lost an afternoon to.

```python
genrule(
    name = "report",
    outs = ["report.txt"],
    cmd = "date > $@ && echo $$USER >> $@",
)
```

The output of this rule depends on the current time and the current user, but
neither is in the action key — `genrule` doesn't capture either by default.
So Bazel cached the first run forever. CI ran as `runner`. My laptop ran as
`mira`. The committed report belonged to whichever environment lost the race.

The fix is one of:

- Stop reading `$USER` and `date` (correct).
- Declare them in `env` so they enter the key (sometimes correct).
- Pass them in as input files generated by another rule (always correct).

## Stamping is not caching

Bazel has a separate concept called **build stamping** — `--stamp`,
`workspace_status_command`, the volatile/stable status files. Stamping injects
build metadata (git SHA, timestamp) into specific outputs *without* feeding
them into the action key, so caches don't bust on every commit.

If you find yourself wanting to put the git SHA into a binary, that is what
stamping is for. Reaching for `--action_env=GIT_SHA=...` instead will work,
but it will also defeat your remote cache for every action that touches that
variable.

## How to inspect a key

When a rebuild surprises you, this is the command:

```sh
bazel build //some:target --execution_log_json_file=/tmp/log.json
jq '.[] | select(.targetLabel == "//some:target")' /tmp/log.json
```

The execution log spells out, per action, exactly which inputs and env
variables Bazel hashed. Diffing two of these between machines is the fastest
way to find the leaky one.

## The mental model

Cache keys are not a black box. They are a precise statement of *the function
this action computes*. If two invocations should return the same bytes, the
key should match. If they should not, an input is missing — and that is a
bug, not a quirk.
